Case study

GenAI-GE

A game engine with one hard coded system. The renderer draws whatever it is handed, and everything that would normally be gameplay code is invented at runtime by six agents reacting to a sentence the player typed.

Solo project, December 2024. This page describes a snapshot exactly as it stands: six recorded turns, no test suite, and four limits that are properties of the design rather than bugs waiting to be fixed.

If systems are just functions that read state and write state, a model can be a system.

An entity component system splits a game into data and the functions that transform it. Position, health, whatever the game needs, held as plain components, and systems that sweep over them each frame. It is a clean split, and it has an obvious provocation buried in it: nothing about a system requires it to be code. It only has to read the relevant state and write back a change.

So I built one where they are not code. The player types anything at all. No parser, no verb list, no command grammar. If nothing in the game knows what the sentence means, a model invents the rule that would make it mean something, writes that rule down in English, and the rule is then executed, by another model, on that turn and every turn after it.

Nothing here has a card game in it. There is no card database, no deck logic, no notion of a hand. In the recorded session a player typed that they wanted to play Yu-Gi-Oh, and the system built one out of nothing but its own invented rules. That is the thesis working. The rest of this page is what happened next, which is where it gets useful.

01

The whole engine

Six agents in a fixed chain, one straight line, no branching and no parallelism. The only thing drawn in a solid box is the renderer.

Dashed boxes are model calls. Everything solid is the small amount of the engine that is actually code.

02

What one turn does

The player's sentence goes in at the top and each stage waits for the one before it.

1

The Game Master shapes the fiction

Before answering it makes the browser screenshot its own canvas and looks at the picture alongside the state. It decides where the game should go next and creates whatever the fiction now needs to exist. This is the agent that invented five specific card names out of nothing.

Larger model, high temperature
2

The Supervisor decides which rules must exist

It reads the input and the list of rules already invented, and writes any missing ones as short English paragraphs: what the rule is for, how it behaves, and what data it assumes. That paragraph is the entire implementation. It goes into a registry and is read back as instructions from then on.

Larger model
3

Transition creates the data the new rules assume

A rule about drawing cards is meaningless if nothing has a deck. This stage adds the missing components before anything tries to use them.

Small model
4

The Resolver runs every rule that has ever been invented

One model call per rule, in sequence, each one told that it is that rule and handed its own paragraph as its instructions. This is the stage that grows, and it is the centre of the cost problem further down this page.

Small model, once per rule
5

The Canvas Adjuster compares the picture to the intention

It applies everything pending, pushes the new state to the browser, waits for a redraw, takes a second screenshot, and looks at both frames. If the board does not show what the fiction said happened, it patches the board. This is the most interesting agent in the chain and also where the recorded turn breaks.

Small model, two images
6

The Narrator says what happened

It reads the results and the state and writes a short description for the player. Notably it does not read the Game Master's directive, so it reports the state it finds rather than the story that was intended.

Small model
03

The turn that contains the whole thing

Turn two of six. The previous turn had cleared the world and invented a single rule about card games. Now the player types that they want to see their deck and draw the top five cards.

The Game Master answers with five card names and puts them in front of the player. There is no card database anywhere in the project. Those five names exist because a model wrote them into a component value and the engine stored them without knowing what they were. The Supervisor decides that a deck rule and a rendering rule now have to exist and writes both as English paragraphs. Transition puts an empty deck and an empty hand on an entity. The Resolver runs three times, once per rule, and all three return the same two writes. The Canvas Adjuster looks at the board, sees no cards on it, and draws five itself, one per invented name.

Then the Narrator tells the player their deck is empty.

Both statements are the system's own output, seventeen seconds apart, inside one turn. The five agents each held a slightly different idea of which entity the player's hand was, and the last one to write won. That single turn is the thesis and the flaw at the same time: a game invented a deck, invented the rules governing decks, executed those rules, looked at the resulting picture, judged it wrong and fixed it, all without a line of card game code existing anywhere. And then it lost track of what it had just made.

04

Where the architecture breaks down

Four limits, all visible in the code and in the recorded session rather than inferred. None of them are bugs I did not get around to. Each one is the direct cost of having no hard coded rules, and the numbers below come from the six turns that were recorded.

1, 3, 4, 4, 7, 10model calls the resolver made on each of the six turns, set by the player's history rather than by the current input
7 sof every turn spent in fixed waits for the browser to redraw and upload, before any model is asked anything
8 → 125rows in the entity store from the first turn to the last, including duplicates of entities that were already there
Limit 01

Nothing overlaps

The chain is a straight line with a hand written router and no parallel edges. Every stage waits for the one before it. The two largest, slowest model calls sit at the front, where nothing can proceed without them, and seven seconds of every turn are fixed sleeps waiting on the browser. The recorded turns land between one and four minutes apart. Some of that is the player typing. The trend is the pipeline.

Limit 02

Cost grows with everything ever asked for

The resolver loops over every rule that exists, one call each, every turn. Rules are never checked for relevance. A mana rule invented for a fireball three turns ago is still asked what it would like to do while the player is shuffling a deck. The curve is set by the player's history, and the input is the only thing that could tell you which rules actually matter.

Limit 03

Rules accumulate and are never retired

Nothing in the design can shrink the list. No agent is ever asked whether a rule is still needed, and the actions available to them operate on entities and components, not on rules. There is a note in the code where the cleanup stage should be, and no cleanup stage. By the final turn the registry held ten entries for seven distinct rules, so three of those ten calls paid full price to re-run a duplicate.

Limit 04

Identity is a suggestion, not an address

This is the one that decides whether the fiction holds together. Two hard coded roles are the safety net for a model that has lost track of an id, which works for the two entities the game starts with and for nothing it ever invents. Worse, agents routinely send the name they chose where the engine reads an id, so the name is discarded at the door and the thing they just created cannot be addressed by the only handle they know.

There is a fifth problem that is not architectural but shapes how much of the above you see when it runs. Component payloads are not validated, so the engine accepts a shape the renderer cannot read. Most of the entities created during the recorded session were written into the world and never drawn. And a directive written by the first agent reaches one of its three readers, because two of them read a field name that is never assigned anywhere: those two agents, the ones deciding what rules exist and what they do, were working from the player's text alone. A good part of the incoherence in the recording has that at the root.

05

What the limits taught

The first three limits are the price of the idea, and they need design answers rather than fixes. A relevance pass would decide which rules run this turn instead of broadcasting to all of them. Retirement would let a rule that has stopped mattering leave. Merged or parallel calls would stop the cost of a turn tracking the length of the session.

The fourth is the one I would build first. An identity layer gives names that resolve to ids, ids the models are required to echo back, and a refusal when they do not. That is what would let the same deck still be the same deck five turns later, and almost everything that went wrong in the recorded session goes back to its absence.

The larger lesson shaped everything I built afterwards. An unbounded surface produces exactly this: impressive on turn one, incoherent by turn six. Power Engine is the same idea with the surface deliberately narrowed until it holds. There, a model may only change values, descriptions and availability inside a character that already exists, the world's rules are written prose rather than invented per turn, and every change goes into an append-only log that a test can assert on. I kept the conviction and reversed the constraint.

Two pieces of writing came out of continuing to pull on this. The snapshot on this page implements neither of them, and it has no test suite behind it either.
