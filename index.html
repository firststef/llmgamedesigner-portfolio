I design games whose rules are written while you play.

Two projects, four years apart, asking the same question from opposite ends: how much of a game can a language model decide without the game stopping making sense. One puts a model inside a fighting game's rules. The other gives it the whole engine and keeps only the renderer.

01

Power Engine

Godot 4.6 · in development

A 3D turn-based fighter where each character is a program, and speaking in character is how you edit it.

A fighter can spend a turn talking instead of attacking. Twelve words, and the speaker is committed for six ticks, so a line can be interrupted by a fist. Two models read what was said: a small one decides whether the thought is finished and worth judging, a larger one decides what it costs and what it grants.

What comes back is a patch to the speaker's own character program. Combat reads that program live, so the fight after the patch is not the fight before it. The rules of the universe are prose shipped with the scenario, never engine code, which is why the same sentence can be refused in one world and rewarded in another.

02

GenAI-GE

JavaScript · December 2024 · snapshot

A runtime engine where the only hard coded system is the one that draws the screen.

The player types a sentence. There is no parser and no verb list. Six agents run in a fixed order: one shapes the fiction and looks at the screen, one decides which rules have to exist and writes them out in English, one creates the data those rules assume, one runs every rule that has ever been invented, one compares the picture to the intent and fixes the board, one narrates the result.

It is a snapshot from December 2024 and it has six recorded turns behind it, no tests, and four structural limits I can point at in the code. Those limits are the reason this page exists. They are what the idea costs, and they are specific enough to design against.

03

How I work with models in a game

Rules as data

The world's rules are prose, not code

A scenario ships a plain-language description of how its universe works, and the model reasons over it. New behaviour is added by editing that text. Nothing in the engine knows what a vow is.

Bounded surface

A model edits values, not behaviour

The judge changes numbers, descriptions and what is available. It does not author new executable behaviour. That boundary is what makes the output safe to apply live and cheap to verify.

Evidence

Every change is logged and replayable

Loading a character means loading the base program and replaying its history. The log is the story and the audit trail at once, which is also what makes the automated tests possible.

Latency is design

Cheap model first, expensive model rarely

A small model gates the expensive one so most turns never pay for judgement. The wait that remains is shown to the player as the world taking a moment to acknowledge what was said.

Failure

Degrade to a playable game

Server down, timeout, malformed reply: the fight continues without the narrative layer, and the AI opponent simply stays quiet. A model is a feature, not a dependency.

Limits

State the parts that are not built

Breach detection for conditional vows is not implemented. Restrictions about targeting do not map onto the availability mechanism. Both are written down rather than talked around.
